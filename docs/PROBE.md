## 0. Verdict first — the decomp gap is no longer the blocker

**gbarecomp is a credible vehicle for a native FoMT Android port, and it
flips the project.** Instead of hand-decompiling ~2,700 Thumb functions
over years, `gba_recompile` translates the ROM's ARM/Thumb machine code
into native C++ automatically and links it against a shared GBA hardware
runtime. The StanHash/fomt decomp — 20% complete, the thing that made the
earlier probe say HARD — is **optional, not required**: the function
finder discovers functions from the ROM itself (WL4: 32,804 functions
emitted from 4,086 seeds; Mega Man Zero ships with zero decomp input).
The decomp's remaining value is readable names/debug metadata and the
authoritative code/data split — and it only contributes if it builds a
byte-matching ROM.

What replaces the decomp as the work: **static-coverage iteration**
(finder + TOML hints + strict-mode abort loop until `FULLY_STATIC`),
**three runtime gaps** (mosaic missing; raster-split mechanism to verify;
SRAM stack-copy handling), and the Android packaging already proven by
Wario Land 4. Difficulty moves from "multi-year decomp project" to a
**bounded port project** — but it is still beta software, and FoMT has
never been run through it. The translation run against Ray's ROM is the
proof step; nothing here substitutes for it.

## 2. How gba_recompile works (ROM in → C++ out)

- Tool: `tools/gba_recompile/main.cpp`, built as the `gba_recompile`
  target; CLI wrapper `tools/cli.py`. Cart mode:
  `gba_recompile --rom <rom.gba> [--entry HEX] [--symbols TSV]
  [--data-symbols TSV] [--config TOML]... [--out DIR]
  [--rom-base 0x08000000] [--max-functions N] [--codegen-shards N]
  [--output-prefix ID]`. BIOS mode: `--bios <bios.bin>`,
  `rom_base=0x00000000`.
- Outputs: `recompiled_NNN.cpp` shards (2–256 TUs; "Monolithic cart
  output is prohibited"), `recompiled.h`, `dispatch_table.cpp`
  (`kDispatchTable`, PC → native function pointer), `symbol_map.cpp`,
  `data_symbol_map.cpp` (debug only, with `--data-symbols`).
- **Function discovery — no decomp needed.** Two seed sources
  (`src/recompile/function_finder.h:39-41`): the ROM-header entry point,
  and seeds (entry_point from game.toml, imported decomp symbols). The
  finder (`function_finder.cpp`, 3,439 lines) follows control flow from
  seeds (direct branches/calls, ARM/Thumb interworking via BX/BLX,
  fall-through after conditional indirect transfers), harvests literal
  pools for code pointers, runs an AOT scan over a bounded executable
  range for callback tables, and auto-detects jump tables (absolute-32
  and Thumb-offset forms, bound-validated). Manual hints in game.toml:
  `[[extra_func]]` (incl. `resume = true` interior seeds),
  `[[jump_table]]`, `[[data_range]]` (bytes that are data, never code),
  `[[exclude_func]]`, `[[code_copy]]` (RAM-relocated code).
  `static_resume_all` (default `true`) adds a static dispatch/resume
  entry for every aligned instruction inside each emitted body, so
  IRQ/SWI returns can resume at any instruction boundary.
- **Data: the ROM is NOT embedded.** Generated C++ contains only
  translated code; data lives in the ROM image, which the runtime loads
  from a file at startup and keeps as a byte array behind the bus
  (`GbaBus::set_rom`, `src/gba/gba_bus.h:127`; ROM load + SHA-1
  verification in `src/runtime/runtime.cpp:1549-1703`). Guest data
  accesses are ordinary bus reads against the loaded ROM bytes.
  `[[data_range]]` entries only tell the finder "don't decode these
  bytes as code". **Consequence: the earlier probe's data blocker (1,626
  `.incbin "baserom.gba"` slices, no extraction pipeline) evaporates —
  no extraction pipeline is needed at all.** The ROM file is the data
  store, supplied by the player, exactly as in the WL4 public builds.
- Generated code is "evidence, not authority: if output is wrong, fix
  the analyzer/emitter and regenerate rather than editing generated
  files" (`README.md`).

## 3. The decomp is optional — what it does and doesn't contribute

- WL4 measured (`variants/warioland4/generated/recompiled.h`): **32,804
  functions emitted from 4,086 seeds** — 24,003 synthesised `tfunc_` /
  `afunc_` names, 4,715 jump-table targets the finder found itself.
  Dispatch table: 235,011 entries (includes per-instruction resume
  entries). Engine docs (`docs/SYMBOL_OVERLAY.md`): "A recompiled game
  is, by default, anonymous… names are identifiers and debug metadata."
  Precedent: Mario Kart: Super Circuit, 13,717 functions, 137 names.
- The decomp's actual WL4 contribution: **588 meaningful names** (of
  4,086 imported symbols; 3,489 are `func_80xxxxx` placeholders, 9 are
  `sub_…`), 4,086 boundaries, 1,193 data symbols, and **one
  `[[data_range]]`** (`0x08095138–0x0878F970`, "non-executable
  (sections)") — the authoritative code/data split, which the WL4 team
  calls the load-bearing part (they deliberately omit `aot_scan`
  bounds because "the imported decomp boundaries are the authoritative
  code/data split, and a hand-bounded range risks decoding assets").
- **Hard gate:** the decomp must reproduce the target ROM **byte-for-byte**
  (md5 check in regen) or its symbols are unusable — `gba_recompile`
  aborts on sha1 mismatch. A 20%-decompiled FoMT that builds a matching
  ROM still yields boundaries for everything its ELF labels; a FoMT
  decomp that does **not** yet build a matching ROM contributes nothing
  and the project runs finder-only (Mega Man Zero precedent: zero decomp
  input, ships). Whether StanHash/fomt currently builds a matching ROM
  is **unverified** — the earlier probe never ran `make compare` (no ROM
  was available). That is the first thing the translation run settles
  (§9, step 0).
- The unidentified 542-function subsystem, the 179k-line event/script
  dispatcher, the game-state machine, the IWRAM IRQ blob — all become
  translation input, not hand-decomp work. The IWRAM blob in particular
  stops being a blocker: the translator reads it from the ROM, so the
  IRQ dispatcher and `func_030004DC` become translated functions, and
  the DISPCNT setup hidden in the blob becomes observable via oracle
  diffs instead of guesswork.
- StanHash/mary (script compiler/decompiler, 97.59% of FoMT scripts
  decompile exactly) stays a later tool for script work/modding, not a
  port input.

## 4. Strict-static mode — genuinely achievable, per-game, not free

- Env var **`GBARECOMP_STRICT_STATIC=1`** (not a build flag). Three
  interlocking effects: `overlay_loader.cpp:430-441` sets the self-heal
  loader inactive before even inspecting the overlay cache; any
  interpreter execution aborts (`runtime_arm_default_aborts.cpp:158-166`,
  "STRICT_STATIC … interpreter execution for pc=0x… is forbidden");
  any dispatch miss aborts (`:1267-1271`). `GBARECOMP_FORCE_INTERP` +
  strict is rejected at startup (`runtime.cpp:1849-1858`).
- **Proven on real games.** `GBA_ACCURACY_BURNDOWN.md` (2026-06-28
  sweep): "MinishCap boots fully native (0 interpreted, 0 dispatch
  misses)". Doctrine (`PRINCIPLES.md:117`): acceptance and
  coverage-regression runs set `GBARECOMP_STRICT_STATIC=1`; "A successful
  strict run proves the linked static corpus covered every executed PC."
  The runtime dumps a machine-readable coverage report at every exit —
  `COVERAGE: FULLY_STATIC` vs `NOT_STATIC`, with distinct-miss /
  interpreted-instruction / healed-to-native counters. A build may NOT
  be described as "fully native" while any guest PC was interpreted or
  served from the code cache.
- **What it takes for FoMT:** complete static coverage is a *work item*.
  Entry seed + flow-following + literal-pool/callback harvesting + auto
  jump tables + TOML `[[extra_func]]` / `[[jump_table]]` hints for
  anything indirect (function-pointer tables, state-machine dispatch —
  common in a farming/life-sim with many scripted event handlers), plus
  `static_resume_all` left on. Each strict-mode abort names the missing
  PC; the loop is add seed/hint → regenerate → re-run strict. The
  runtime emits a TOML fragment proposal per run
  (`recomp_master_misses_<tag>.toml.frag`, `runtime.cpp:1120-1135`).
- **Where it stops:** genuinely dynamic code. Self-modifying /
  dynamic-RAM code is "out of scope until the static common case is
  GREEN" (burndown Axis 6). A pure-static build is achievable **iff**
  FoMT's executed code is all ROM-resident and statically discoverable
  (plus declared `[[code_copy]]` RAM overlays, §5).
- **Android wrinkle:** on-device, `mobile_prepare_process` defaults
  `GBARECOMP_SELFHEAL_RECOMPILE=0` ("a device has no toolchain, so
  dispatch misses are bridged by the interpreter LOUDLY, logged to the
  miss list/coverage report… and fed back offline")
  (`src/runtime/mobile_platform.h:4-15`). The shipped FoMT APK must
  therefore pass strict-static on desktop *before* it is acceptable on
  Android; the Android default makes any coverage hole loud rather than
  silent — the right safety net during development, not a shippable
  state.
- Note (worker B): the `strict = true` key in a `game.toml`
  `[recompiler]` table is **not consumed** by `gba_recompile` — that
  whole table is documentary; real inputs are CLI flags and the runtime
  env var.

## 6. FoMT-specific risks (the actual work list)

1. **Mosaic missing (§5).** FoMT's fade system writes MOSAIC
   (`asm/hardware.s:3642`) as part of transitions. The PPU has no mosaic
   path at all. Fix = implement mosaic in the engine's PPU (a contained
   renderer feature, contributed to the engine fork) — or prove FoMT's
   mosaic use is cosmetic and defer it. Cannot be config-fixed.
2. **Raster split — mechanism to confirm.** The split writes BG2CNT
   during HBlank (busy-poll on DISPSTAT), which the scanline-granular
   renderer handles. But if any FoMT effect writes PPU registers
   mid-visible-line, it renders wrong until a per-pixel/mid-line resync
   path lands (burndown Axis 5 lever, unbuilt). Confirmation = the
   translation run + oracle frame diffs on the affected scenes.
3. **SRAM stack-copy routines — the one FoMT-specific strict-static
   risk.** FoMT copies its SRAM read/write/verify routines to the
   **stack** (0x80/0xC0 bytes) and executes them there
   (`asm/code_lib_sram.s`, `func_080D379C/080D3800/080D3870`), a GBA
   hardware quirk (code must not run from ROM while SRAM timings are
   forced). A translator cannot pre-declare a stack address via
   `[[code_copy]]` (that mechanism is for fixed RAM addresses, e.g.
   the m4a `SoundMainRam` 0x400-byte mixer copy — a standard m4a
   pattern, declared the same way). The likely fix is a small per-game
   patch: replace the stack-copy call with a direct call to the
   recompiled function (same class as WL4's ROM-gap gameplay tweaks,
   §7), or HLE the SRAM access at the bus level. Bounded (4 small
   functions), but it is the one place strict-static may need a patch
   rather than a hint. It must be tested in the translation run —
   whether the dispatch-miss path even triggers depends on how the
   recompiled copy loop interacts with the dispatch table.
4. **SWI 0x2A** (§5) — one-line clarification, non-blocking under LLE.
5. **HBlank DMA ordering** — HBlank DMA fires after the line renders
   (matches hardware). FoMT has no HBlank DMA evidenced (only the
   HBlank poll), so low risk; re-check if the translation run shows a
   one-line offset in any effect.
6. **Generated-code scale.** WL4 (8 MiB ROM): 4.86M lines / 196 MB in
   16 shards, 32,804 functions. **CORRECTION 2026-11-21: FoMT's ROM is
   8 MiB (0x00800000), not 16 MiB as assumed here** — the first real
   translation run proved it (1,107 functions discovered, 2 shards
   emitted). Generated-code scale will be WL4-scale, not ~2x WL4; cap
   native compile jobs (`-PgbaNativeJobs=2` on a 4 GB machine) and 16 KB
   page alignment for Android 15+ still stand.
7. **BIOS dump still required** even with HLE on (no-BIOS tier
   deferred). The Android setup flow must ask the player for their BIOS
   dump, as the existing builds do. The earlier probe's "no-BIOS"
   assumption is wrong — correct it in the plan.
8. **Stale-doc trap.** `docs/ROADMAP.md` checkboxes lag the code
   (bitmap modes, HBlank DMA, timer cascade, save detection all landed
   after being listed TODO). Trust source files + burndown over the
   roadmap.

## 7. Wario Land 4 reference — what a shipped recomp looks like

- **Layout** (`Gitsnup/warioland4-recomp`, HEAD `f7c347d`, 3,011 files):
  `gbarecomp/` (vendored engine fork, PolyForm), `recomp-ui/` (MIT,
  Dear ImGui launcher), `decomp/` (lilDavid/warioland4, MIT),
  `variants/warioland4/` (game.toml, symbols/, generated/ — 196 MB,
  committed), `android/` (Gradle project), `src/` (game shell:
  `main.cpp`, `game_launcher_boot`, `wl4e_rom_identity.h`,
  `wl4e_song_classes.h`), `tools/` (regen.sh, tweak gen, mod tools),
  root CMakeLists + MIT LICENSE. `roms/`, `bios/`, `saves/`, `mods/`
  are user-supplied, gitignored, never committed.
- **Vendoring vs submodules:** `gbarecomp/`, `recomp-ui/`, `decomp/`
  are vendored copies (their `.git` parked out of tree), not submodules.
  Inside gbarecomp, 4 real submodules are populated: `external/
  arm-recomp-core`, `external/recomp-net`, `external/rbengine`,
  `platform/android/third_party/SDL` (Gradle fails loudly if missing).
  `decomp/tools/agbcc` is gitignored and fetched at build time.
- **Regen pipeline** (`tools/regen.sh [--jobs N] [--skip-decomp]`):
  1. ROM md5 gate (`5fe47355…`, WL4 USA) + SHA-1/CRC32 compute.
  2. Stamp SHA-1/CRC32 into `game.toml`, `game_android.toml`,
     `build.gradle`, generate `wl4e_rom_identity.h`.
  3. Build the decomp with agbcc (unless `--skip-decomp`); rebuilt ROM
     md5 must match retail or abort.
  4. `arm-none-eabi-readelf -sW/-SW` + ld map →
     `import_decomp_symbols.py` → `imported_symbols.tsv` (4,086),
     `function_boundaries.tsv`, `imported_data_symbols.tsv` (1,193),
     `WL4E_symbols.toml` overlay (one `[[data_range]]`).
  5. `gba_recompile --rom … --config game.toml --config
     WL4E_symbols.toml --symbols … --data-symbols … --out generated/`
     → 16 shards + `dispatch_table.cpp` (235,011 entries) + symbol
     maps, 4.86M lines / 196 MB. Then CMake: desktop exe, or `libmain.so`
     on Android (target must be named `main`).
- **Android APK:** Gradle + NDK 27.1 + CMake 3.22.1, minSdk 28,
  release arm64-v8a only; `libmain.so` (game + generated shards) +
  `libSDL2.so` + `libc++_shared.so`, 16 KB page-aligned. **Public APK
  ships no ROM/BIOS** — first-run `GbaSetupActivity` collects the dump
  via the Storage Access Framework, SHA-1/size-verifies it, copies it
  to app-private storage. Private builds use `-PprivateRom=` (SHA-1 +
  size gate at Gradle time, output renamed
  `*-PRIVATE-rom-included.apk`). Touch via SDL fingers → engine
  virtual pad (D-pad/A/B/Start/Select/L/R) + gamepad, landscape-locked.
  Audio: SDL opened at 65,536 Hz mono S16 (32768 caused half-speed
  playback). Saves: `<files>/saves/warioland4_usa.sav`, flushed ~1 s
  after last write / max ~10 s, atomic tmp+rename. Hard-won Android
  lessons: 16 KB page alignment (Android 15+ loader kills 4 KB-aligned
  `.so` instantly), game-thread stack (256 MiB pthread; SDL's main
  thread is ~1 MiB), build memory (`gbaNativeJobs=2` on 4 GB machines),
  SDL submodule gate, release signing via keystore props.
- **Per-game work WL4 needed** (FoMT would need the same class):
  widescreen margin provider reading the game's own BG map arrays;
  gameplay tweaks via a Thumb helper injected into a ROM zero-gap
  (`tools/wl4_tweak_gen.py` → `tweaks_patches.h`, applied to the
  in-memory ROM copy at boot, dump stays pristine); MP2K song-table
  classes (566 songs) for Music/SFX split mute; content-mods plumbing
  (soundfont/skin/palette re-applied every frame). **No per-game audio
  or save code** — the game's own m4a engine runs recompiled and generic
  32 KiB SRAM covers WL4. FoMT's analogue: a `game.toml` +
  `game_android.toml` + ~150-line `main.cpp` shell, ROM identity, a
  regen.sh clone, symbol import if/when the decomp matches, and
  FoMT-specific tweaks/mods only if desired. Widescreen for FoMT is
  optional and complicated by the raster split — defer it.
- **Siblings (brief):** MegaManZeroRecomp (mstan, Windows-only, **zero
  decomp input**, "playable static-first bring-up", interpreter fallback
  for uncovered paths) — proof a game ships with no decomp at all.
  Golden Sun Recompiled (GSRecomp, edited engine copy, dual-game
  launcher, experimental ARM64 Android port v0.9.1 privately delivered,
  touch controls + save transfer between games) — no different

## 8. Reworked repo plan — the decomp-first phasing is wrong

### What survives from the earlier scaffold

- Overlay structure: port-only code + fetch/build scripts in Ray's
  repo; upstream source not vendored as project code (gbarecomp arrives
  as a **pinned submodule**, per the toolkit's own documented
  convention; the fomt decomp arrives fetch-at-build, pinned
  `b8471ae06`, only as a symbol source).
- `.gitignore`: ROMs, BIOS, extracted data, `third_party/`, build
  outputs, `generated/` (WL4 commits generated/; FoMT should NOT —
  generated C++ is ROM-derived and must not be redistributed, §1).
- Android shell shape (Gradle + touch controls + JNI) — but the shell
  is now the gbarecomp SDL-based one (`GbaGameActivity` /
  `GbaSetupActivity` / `libmain.so`), not a custom shim activity.
- "User supplies their own ROM, hash-checked" (RR64-style) — now with
  the WL4 setup flow (SAF picker + SHA-1/size verification) instead of
  a build-time-only gate. Plus: the user also supplies their own BIOS
  dump (required even with HLE on, §6.7).
- SRAM save sizing (32 KiB, 2 slots) and the still-open slot-count pin
  (2 vs 3) — the `[save]` TOML + `saveBytes` need the pinned count
  before the Android save path is final.

### What is replaced

- **Decomp-first phasing → coverage-first phasing.** No months of hand
  decomp before a native build exists. The decomp becomes an optional
  symbol source, matured in parallel if at all.
- **`native/shim/` (custom tile renderer, m4a/PSG audio, input,
  VBlank pump, BIOS SWIs, DMA, SRAM file) → deleted as a concept.**
  The gbarecomp runtime *is* the shim, already written and validated on
  harder titles. Do not write a second one.
- **`native/game/` (port-owned ARM64 game code, empty until decomp
  lands) → `generated/` (build output, gitignored).** The game code is
  produced by `gba_recompile`, not written by hand.
- **`native/data/` (user-ROM extraction pipeline) → deleted.** Data
  stays in the player's ROM file at runtime (§2); no extraction
  pipeline is needed or wanted.
- **"Fake GBA address space for hardcoded pointers" → deleted.** The
  runtime's bus *is* the GBA address space; recompiled code reads ROM/
  RAM through it.
- **First build step changes:** `make compare` on the decomp is still
  step 0 (it proves ROM identity and whether the decomp can feed
  symbols), but it no longer gates the port — a failing `make compare`
  just means finder-only mode (Mega Man Zero precedent).

## 9. What the translation run needs + exact commands

**Cannot be done in this probe: the actual translation run needs Ray's
own US ROM dump** (SHA-1 `a2fc3574f0a65a4fcf7682fb274b9d7eebdef963`).
Never suggest downloading one. Everything below runs on Linux (or
WSL2/MSYS2 on Windows) once he supplies it.

Step 0 — decomp sanity (tells us whether symbols are available):
```
git clone https://github.com/StanHash/fomt
# MSYS2 + devkitARM (arm-none-eabi) + notyourav/agbcc branch cp
#   via tools/install_agbcp.sh; place Ray's ROM as baserom.gba
make compare        # expect OK + sha1 match; a fail means finder-only mode
```

Step 1 — build the recompiler (from the FoMT repo, after scaffolding):
```
cmake -S gbarecomp -B gbarecomp/build
cmake --build gbarecomp/build --target gba_recompile -j$(nproc)
```

Step 2 — symbol import (only if step 0 passed):
```
arm-none-eabi-readelf -sW decomp/build/fomt.elf > symbols/readelf_syms.txt
arm-none-eabi-readelf -SW decomp/build/fomt.elf > symbols/readelf_sections.txt
python3 gbarecomp/tools/symbol_import/import_decomp_symbols.py \
  --id FOMT --name "Harvest Moon: Friends of Mineral Town (USA)" \
  --syms symbols/readelf_syms.txt --sections symbols/readelf_sections.txt \
  --map decomp/build/fomt.map --rom <ray's ROM> --out variants/fomt/symbols/
```

Step 3 — translate (finder-only if step 0 failed: omit --symbols/--data-symbols):
```
gba_recompile --rom <ray's ROM> \
  --config variants/fomt/game.toml \
  [--config variants/fomt/symbols/FOMT_symbols.toml] \
  [--symbols variants/fomt/symbols/imported_symbols.tsv] \
  [--data-symbols variants/fomt/symbols/imported_data_symbols.tsv] \
  --out variants/fomt/generated
```

Step 4 — build + strict-static acceptance run (desktop):
```
cmake -S . -B build-desktop -DCMAKE_BUILD_TYPE=Release
cmake --build build-desktop -j$(nproc)
GBARECOMP_STRICT_STATIC=1 ./build-desktop/FoMTRecomp --frames 3600   # ~1 min of play
# exit report: COVERAGE: FULLY_STATIC | NOT_STATIC, distinct misses,
# interpreted instructions, healed-to-native counts, and a
# recomp_master_misses_<tag>.toml.frag proposal per missing PC
```

**Coverage numbers that run will produce:** functions discovered vs
emitted (WL4: 32,804 from 4,086 seeds); seeds vs synthesised names;
dispatch-table size; strict-mode aborts by PC (each names the missing
function — the TOML-hint work list); interpreter-execution sites (must
be zero for a shippable build); `FULLY_STATIC` vs `NOT_STATIC` per
run; and, via the oracle harnesses, per-frame/per-scanline/audio diffs
against mGBA/NanoBoyAdvance for the raster-split and mosaic scenes.
